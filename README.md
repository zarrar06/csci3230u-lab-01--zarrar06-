# Instructions

## Part 0 - Setup

1. **Configure Git once** (use the email tied to your GitHub account so commits are attributed to you):
   ```bash
   git config --global user.name "Your Name"
   git config --global user.email "you@ontariotechu.net"
   git config --global init.defaultBranch main
   ```
2. **Authenticate** to GitHub with SSH/HTTPS (recommended) or using a Personal Access Token over HTTPS. Passwords are not permitted in this context.

3. **Clone** the copy you created above:
   ```bash
   git clone <your-repo-url>
   cd <your-repo-dir>
   ```

> Your **local** repo and the **remote** (`origin`, on GitHub) are separate copies. `push` sends commits up; `pull` brings them down; `clone` made the first copy. Run `git remote -v` to see where `origin` points.

## Part 1 - Issues: plan the work

Before you write code, say what you're going to do. A GitHub **Issue** is a tracked unit of work - a task, a bug, or an idea - with its own discussion thread and number. Teams plan and divide work through issues, then link the code that resolves them.

Create your first issue:

1. On your repo, go to the **Issues** tab → **New issue**.

2. **Title:** `Add my favourite language`. In the body, describe the change in a sentence.

3. *(Optional)* add a **label** (e.g. `enhancement`) and **assign** it to yourself.

4. Submit - it gets a number, **#1**. You'll close it automatically when your PR merges (part 3).

**Linking code to issues** - mention an issue number in a commit or PR and GitHub links them:
- `Refs #1` - references the issue (leaves it open).
- `Closes #1` / `Fixes #1` / `Resolves #1` - **auto-closes** the issue when the commit/PR lands on `main`.

> Issues are a project's to-do list. In your group project you'll open one per task, assign an owner, and reference it from the branch, commits, and PR - so the work and the code stay tied together. GitHub **Projects** (a Kanban board built from your issues) is worth a look for planning the group project.  In industry, issues might be generated by a QA team, team leader, project manager, scrum master, etc.

## Part 2 - Commit hygiene & Conventional Commits

Edit `playground.md`, replacing the `TODO` on the last line with a real language. Then stage and commit using the **Conventional Commits** style:

```bash
git add playground.md
git commit -m "feat: record favourite language in playground"
```

Conventional Commits prefix the message with a type - `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`. It's what most teams expect, it makes history scannable, and it's what tools use to generate changelogs and version numbers automatically.

**Rules of good commits** (industry habits):
- **Atomic** - one logical change per commit. Stage files selectively (`git add -p`) rather than staging everything.
- **Imperative, specific messages** - "fix: handle empty board" rather than "fixed bug".
- **Never commit secrets or generated files** - that's what `.gitignore` is for. If you ever *do* commit a key, rotating (revoking) is the only fix, because Git remembers history forever.

## Part 3 - A feature branch and a Pull Request

Real work rarely goes straight to `main`. Branch first:

```bash
git switch -c feat/favourite-language
git push -u origin feat/favourite-language
```

On GitHub, **open a Pull Request** from your branch into `main`. The description box is pre-filled by the template - write a real "what" and "how I tested", and link the issue with `Closes #1` so it auto-closes on merge.

> Branch names carry meaning: `feat/...`, `fix/...`, `docs/...`. Keep branches small and short-lived - a 40-commit branch that's two weeks old will cause merge conflicts that are hard to resolve.

## Part 4 - Continuous Integration

Look at the **Checks** on your PR. The `Lab 01 checks` workflow (`.github/workflows/check.yml`) runs automatically. Right now it's **red**, because `SUBMISSION.md` is still full of `TODO`s.

Fill in `SUBMISSION.md` (on your branch), commit with a `docs:` message, and push. Watch the check re-run and turn **green**.

> This is *continuous integration*: every change is automatically verified. In industry the checks run your test suite, linters, and security scans. A red check means "do not merge."

## Part 5 - Branch protection

In your repo's **Settings → Branches**, add a rule for `main` that:
- **requires a pull request before merging**, and
- **requires the `submission` status check to pass.**

> **Private repositories and branch protection:** protecting a branch in a *private* repo requires GitHub Pro, which students get free through the [GitHub Student Developer Pack](https://education.github.com/pack) - claim it if you have not already. If you are stuck waiting on verification, make the repo **public** for this part (**Settings → General → Change visibility**), add the rule, and switch it back to private afterwards.

Now try to push directly to `main` - GitHub refuses. That's the point: protected branches mean changes can only arrive through a reviewed, checked PR. In industry, this is the norm.

## Part 6 - Merge your pull request

Your PR now has a green check and a real description. Before merging, **review your own diff** on the **Files changed** tab - reading your change as a stranger would catches a surprising amount. Self-reviewing before you ask anyone else to look is a good habit. in your group project, this is the moment you'd request a teammate's review instead.

Then **Squash and merge** - this folds your branch into a single tidy commit on `main` - and delete the branch when GitHub offers. Confirm the linked issue closed automatically.

> Squash-merge keeps `main` readable: one commit per feature, not a trail of "wip", "fix typo", "actually fix it".

## Part 7 - Create and resolve a merge conflict (on purpose)

Conflicts are normal; being calm about them is the skill.

```bash
git switch main && git pull
git switch -c fix/language-a
# edit the favourite-language line in playground.md to one value, commit
git switch main
git switch -c fix/language-b
# edit the SAME line to a different value, commit
```

Merge the first branch into `main` (via PR), then try to merge the second - GitHub reports a conflict. Resolve it: pull `main`, `git merge main` into your branch, edit the file to remove the `<<<<<<< ======= >>>>>>>` markers, then `git add` and commit. Push and merge.

## 8 - The recovery toolkit

Everyone makes mistakes in Git; these commands will be useful:

| Situation | Command |
|-----------|---------|
| Last commit message wrong / forgot a file | `git commit --amend` |
| Need to stash work to switch branches | `git stash` … `git stash pop` |
| Discard changes to a file | `git restore <file>` |
| Unstage a file (keep the edits) | `git restore --staged <file>` |
| "I think I lost a commit" | `git reflog` (then `git switch -c rescue <hash>`) |

Try each once on `playground.md` so that you are familiar with them before you need them under pressure. `git reflog` in particular is invaluable.

# Industry extras (optional homework)

1. **Clean history with an interactive rebase.** Make three messy WIP commits, then `git rebase -i HEAD~3` to squash and reword them into one good commit *before* opening a PR. (Only ever rewrite history that hasn't been shared.)
2. **A professional GitHub profile.** Create a profile README (a repo named after your username), pin your best repos, and write real READMEs. Recruiters look at this - it's your portfolio.
3. **Find a bug in history.** Use `git blame <file>` to see who last changed a line, and `git bisect` to binary-search the commit that introduced a problem.
4. **Team-repo hygiene.** Add a `CODEOWNERS` file, an issue template, and turn on "require branches to be up to date before merging" - all things your group project will benefit from.
5. **Verified commits.** Set up SSH or GPG commit signing so your commits show a "Verified" badge.
